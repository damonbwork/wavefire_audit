# Plan: Persistent, overridable pass/fail with annotation sync

This plan covers a genuinely substantial, multi-part change: making pass/fail a
real, persistent, user-overridable field per attribute-per-sample; tightening
the AI's own logic for when an exception gets written; changing tick marks in
annotations to plain visual symbols that can appear more than once per
attribute per sample; adding two new universal exception rules; and keeping a
user's override in sync with any already-annotated files, with a warning
before overwriting anything.

Every piece below is grounded in the actual, current code — not written in
the abstract — since several of these changes touch structure that already
exists and needs to change carefully, not be replaced wholesale.

## Current state, as it actually exists today

- **The AI's own output is one result per attribute per file**, not an array
  of marks. The exact schema Claude is currently asked to return is:
  `{"results":[{"title":..., "result":"pass"|"pass_exception"|"fail",
  "note":..., "reasoning":..., "sourceFile":..., "page":1, "section":...,
  "paragraph":2}]}` — one object per attribute, `result` is one of exactly
  three values, and there is no concept today of multiple, separate marks for
  one attribute within one sample.
- **Pass/fail/exception status is not currently persisted as an editable
  field.** It lives in `_wpAnalysisResults[ref]`, an in-memory structure
  rebuilt fresh every time Analyze runs. There is no database column today
  that stores "this attribute's result for this specific sample, as
  currently overridden by a person" — nothing to overwrite even exists yet.
- **`workpapers.exceptions`** is a real, existing JSONB column — an array of
  exception objects, each with its own `id`. This is a genuinely separate
  concern from the per-attribute `result` field above; today nothing
  enforces that a `fail` or `pass_exception` result actually has a
  corresponding entry here, or vice versa.
- **Four separate mechanisms burn or attach annotations to sample files**,
  each independently reading `_wpAnalysisResults` and drawing or attaching
  something based on it: the burned-in inline copy, the form-field copy, the
  Acrobat-comment copy, and the tick-mark-plus-comment copy. All four
  currently draw or write text like "PASS" / "FAIL" / "EXC" as the visible
  label — none of them currently draw a plain checkmark or X, and none
  support more than one mark per attribute per file.

## Part 1 — A real, persistent, overridable pass/fail field

The core problem: pass/fail isn't a property of an attribute alone — it's a
property of *this attribute, tested against this specific sample*. The same
attribute can be tested against several sample files, or several rows in the
sample data grid, and could genuinely pass on one and fail on another. So the
persistent field this plan calls for isn't a single value living on the
attribute's own definition — it needs its own row per (workpaper, attribute,
sample) combination, durably stored, not regenerated by re-running Analyze.

Concretely, this means a new table — something like
`attribute_sample_results` — keyed by tenant, workpaper ref, attribute index,
and a sample identifier (a filename for file-based testing, a row identifier
for sample-data-grid-based testing). Each row would hold: the AI's own
determination (from the most recent Analyze run), whether a person has since
overridden it, what they overrode it to, who did it and when, and the actual
exception text if one exists for that specific result. Analyze writes the AI
determination on every run; a person's override is a separate, protected
field Analyze should never silently clobber on a later re-run without
someone's explicit awareness of what's happening.

## Part 2 — Tightening the AI's own determination logic

Four real, distinct changes to how the model decides pass/fail/exception,
per the exact instructions given:

- **An exception always means the attribute fails.** Today, `result` is one
  free-standing enum value with no enforced relationship between "an
  exception was written" and "the result is fail." This needs to become a
  real invariant: if the model writes exception text for a given mark, that
  attribute's result for that sample must be `fail`, full stop — never
  `pass_exception` with no actual exception behind it, and never a fail
  with an exception that doesn't clearly correspond to it.
- **A noted deviation is not automatically an exception.** The model should
  still be able to observe something worth mentioning — a minor departure
  from ideal practice — and put that observation in the tick mark's own note
  or in Guidance, without writing a formal exception and without failing the
  attribute, when the deviation genuinely doesn't rise to a control failure.
  The distinction is real and needs to be phrased carefully in the prompt
  itself: noting something is not the same act as writing an exception.
- **All three of title, additional information, and pass/fail criteria
  govern the determination — together, not separately.** The prompt should
  make explicit that the model must weigh what the attribute is testing for
  (title), any extra context or nuance (additional info), and the explicit
  pass/fail criteria as one combined picture, not treat pass/fail criteria
  as the only input that matters.
- **Two new universal rules, applying regardless of what a specific
  attribute's own criteria say:**
  - A genuine inconsistency between the sample data grid and what the
    sample files actually show should typically result in an exception —
    the data someone entered doesn't need to be independently tested for
    every attribute if it doesn't match the source documents at all.
  - Sample data that the model cannot actually locate in the sample files —
    not contradicted, simply absent or unfindable — should also result in
    an exception, since untestable data is not the same as data that
    passed.

## Part 3 — Tick marks as plain visual symbols, and more than one per sample

This is a genuine, structural change to the AI's own output schema, not just
a rendering tweak. Today the schema returns exactly one result per attribute
per file. Supporting "more than one checkmark or X for a single attribute in
a single sample" means the schema itself needs to become an array of marks
per attribute per file, not a single object — each mark carrying its own
outcome (pass or fail — visually, just which symbol to draw), its own
location on the page, and its own note, with the attribute's own overall
result for that sample derived from all of its own marks together (any fail
mark present means the attribute fails for that sample, matching the
exception-implies-fail invariant above).

The rendering side needs the same treatment: what gets drawn or attached
should be a plain green check or red X — no "PASS"/"FAIL"/"EXC" text — and
this needs to happen consistently across all four existing annotation
mechanisms, since right now every one of them draws or writes a text label
as the primary visual, not a symbol. This touches real, working code in four
separate places and needs to be done in all four consistently, not just the
one most recently worked on.

**A direct refinement worth capturing here: the symbol and the attribute
number become one combined, compact unit, not two separate elements.**
Now that the symbol itself no longer carries pass/fail/exception text, the
user-assigned attribute number — not any system-generated one — should sit
directly with the symbol as a single small unit, replacing the separate
"[attribute number]" text label currently drawn elsewhere near each mark.
One mark, in one spot, says both "this is a pass" (or fail) and "this is
attribute 7" together, rather than requiring two separate pieces of text
to convey the same two facts. This applies to every mark, across all four
mechanisms, regardless of whether that specific mark is part of an
exception.

**Exception detail is genuinely different content, but should share the
same background, not get its own separate box.** A direct revision to the
framing above: an exception's own number and explanation are still a
different *kind* of content from the symbol-and-attribute-number unit —
free-form text that can run to a full sentence or more — but that doesn't
mean it needs a second, separate white box behind it. Per direct request
to minimize the number of boxes as much as possible: everything belonging
to one tick mark — the symbol-and-number unit, and the exception text when
a mark is genuinely part of one — should sit inside one single, shared
white background, sized to fit whatever that specific mark actually needs,
rather than one small box for the symbol-and-number and a second, separate
box for the exception text beside it. A mark with no exception needs only
the compact symbol-and-number unit and its own single background, sized
small; a mark with an exception needs a taller single background that
fits the additional text too — but still exactly one box either way, not
two.

**The white background itself stays, since it's still genuinely doing real
work — legibility over whatever the sample page itself already shows
underneath.** What's being reduced is the count of separate boxes stacked
per mark, not the background's own presence. This is the same principle
already applied once before to the old pass/fail label specifically —
removing a separate colored accent box that sat behind a white one,
leaving one plain white background as the only layer — now generalized to
every element of a tick mark together: one shared background per mark,
covering everything that mark needs to show, rather than a separate
background for each individual piece of text within it.

## Part 4 — Keeping an override and its annotations in sync

The request here is genuinely reasonable, and mostly buildable directly, but
one piece needs to be named honestly rather than promised as more certain
than it actually can be.

**What's directly buildable, and more precisely than originally stated
here:** when a person changes a result from pass to fail (or the reverse)
for a specific attribute-and-sample combination, WaveFire can look up every
annotated file generated from that same sample and offer to update the mark
drawn for that specific attribute — from green check to red X or back —
matching the new, overridden result.

**A real correction to an earlier overstatement in this plan:** the
original version of this section claimed WaveFire has no reliable way to
detect whether a person already manually changed an annotation, and
proposed a fingerprint-based fallback for all four annotation mechanisms
uniformly. That was an overstatement for three of the four. The honest,
corrected picture, mechanism by mechanism:

- **The burned-in inline copy** is genuinely unreadable in this sense —
  once drawn, it's flattened pixels and vector shapes on the page, with no
  structured data behind it to read back. The fingerprint approach
  described below is the right, honest fallback specifically for this one
  mechanism.
- **The two comment-based copies** (the Acrobat-comment copy and the
  tick-mark-plus-comment copy) use real PDF comment objects, which carry
  their own actual text content as structured, directly-readable data — not
  a picture of text. If a person edits a comment's own text in a tool like
  Acrobat, that edit is sitting in the file's own structure, reachable the
  same way it was originally written. WaveFire can genuinely read a
  comment's current text and directly compare it, word for word, against
  what it originally wrote there — a precise content comparison, not a
  guess.
- **The form-field copy** is the same story — a form field's value is a
  real, addressable piece of data, not a drawing, and reading its current
  text back out programmatically is straightforward.

So for three of the four mechanisms, detecting "has someone already changed
this specific result" can be a genuine, direct comparison of actual content
— what does this field or comment say right now, versus what did WaveFire
itself last write there — not an approximation. Only the burned-in copy
needs the less precise, fingerprint-based fallback described next.

**The fallback, for the one mechanism that genuinely needs it:** WaveFire
can remember the exact state of a file at the moment it last wrote to it (a
simple fingerprint of the file's own bytes right after annotating it). If
the file's current fingerprint still matches that stored one, nothing has
touched it since, and updating it automatically is safe. If the fingerprint
has changed — for any reason, including but not limited to a manual edit —
that's the signal to stop and warn before overwriting, rather than assume
automatically that it's safe. This is a real and useful proxy for "has
someone touched this since" specifically for the burned-in copy, not a
precise "did a human specifically edit the tick mark" detector — while the
warning (or lack of one) for the other three mechanisms can be based on
genuinely knowing what changed, not just that something did.

## Open questions worth deciding before building

- **What counts as "corresponding" sample files for a given override?**
  If an attribute was tested against multiple files, does overriding the
  result update the mark in every one of them, or only the specific file
  the person was looking at when they made the change?
- **Should an override ever get silently reverted by a later Analyze run?**
  Given AI determinations get rewritten on every run, but overrides are
  meant to persist — should the UI show both values side by side when they
  disagree, and require the person to explicitly re-confirm or clear their
  own override after a later run produces a new AI determination?
- **What does "one attribute, multiple marks, one overall result" mean for
  overriding?** If an attribute has three marks in one sample and someone
  overrides the attribute's overall result, does that mean anything for the
  individual marks themselves, or does the override apply only at the
  attribute level, leaving the individual marks exactly as the AI drew them?

## Suggested build order

1. The new persistent table and its own read/write plumbing — the
   foundation everything else depends on.
2. The prompt and schema changes for Part 2 and Part 3 together, since
   they're tightly related — the array-of-marks schema change and the
   exception-implies-fail invariant need to land together to stay
   consistent.
3. The rendering change across all four annotation mechanisms — plain
   symbols, potentially more than one per attribute per file.
4. The override UI itself, writing to the new table from Part 1.
5. The sync mechanism last, since it depends on every earlier piece already
   working — the persistent override field, the new mark-array schema, and
   the updated rendering all need to exist before "find the corresponding
   annotation and update it" is even meaningful to build.
